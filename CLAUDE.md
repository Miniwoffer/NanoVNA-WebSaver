# NanoVNA-WebSaver

A browser application for reading, displaying, analysing and exporting
Touchstone data from a NanoVNA. It talks to the instrument over the Web
Serial API. There is no backend.

## The one rule

**No dependencies and no build step.** The application is vanilla ES
modules served exactly as they are written; `web/` is the document root,
and a change is live on reload. There is no `package.json`, no bundler,
no transpiler and no lockfile, and the test suite runs on plain node with
nothing installed.

Before reaching for a library, assume the answer is a smaller idea. The
whole interface — popovers, a modal, drag interactions, icons, canvas
charts — is a few hundred lines each, written here.

## Commands

```sh
make web-serve          # serve on http://localhost:8000
make web-test           # the whole test suite; needs only node
node web/tests/run.js ./charts.test.js    # one suite
node --check web/js/ui/panels.js          # syntax only
```

`node --check` parses a file as a *script*, so it will not catch every
error in a module (a stray `)` closing an array literal, for instance).
To be sure a module actually parses:

```sh
node --input-type=module -e "import('file://$PWD/web/js/main.js')"
```

## Layout

```
web/
  index.html          the shell; the body is empty and built in JS
  css/app.css         every style, one file
  js/
    main.js           builds the DOM, wires state to the interface
    app/              state, sweep runner, markers, bands, recorder
    charts/           canvas chart engine and the chart catalogue
    device/           Web Serial transport, drivers, detection
    rf/               RF maths, Touchstone, calibration, analyses, TDR
    ui/               DOM helpers and every piece of interface
  tests/              the suite, plus reference vectors and fixtures
```

The interface is a topbar of menus, a grid of chart panels, a marker
overlay floating over them, and a frequency range bar along the bottom.
There is no sidebar.

Notable `ui/` pieces, because they are reused everywhere:

- `dom.js` — `el()`, `field()`, `button()`, `select()`, and friends.
  All text goes in through `textContent`; nothing uses `innerHTML`, so a
  device or a file can never inject markup. Keep it that way.
- `popover.js` — the floating panel every menu and the panel editor use.
- `menu.js` — a topbar button that drops a popover.
- `modal.js` — a native `<dialog>`, used by the calibration wizard.
- `chartgrid.js` — the panel grid; panels span grid cells, hold several
  mini-charts, and are dragged and resized.

## Conventions

- GPL v3 header at the top of every file.
- Comments explain *why*, not what. Match the density of the file you
  are in.
- Charts are drawn on a canvas by the classes in `charts/`; the chart
  catalogue in `charts/registry.js` is data, not code.
- Settings live in `localStorage` and are normalised on load — see
  `normalizeLayout` in `charts/registry.js` and `normalizeMarkers` in
  `app/markers.js`. Anything read back from storage may be from an older
  version: never throw, fall back to a default.
- The RF code is a port of the upstream NanoVNA-Saver desktop
  application. It is the specification: keep the two agreeing, and check
  against the reference vectors rather than against your own reasoning.

## Testing

`web/tests/` runs under plain node — no framework, no runner to install.
`harness.js` gives `describe`/`it`/`assert`; `run.js` takes suite paths.
Add a suite to the `web-test` target in the `Makefile` when you create
one.

- `reference.json` holds vectors generated by the desktop application
  and by numpy/scipy.
- `data/` holds the Touchstone and calibration fixtures from its test
  suite.
- `fakecanvas.js` is a no-op canvas so the real chart drawing code can be
  exercised without a browser.

A test that fails against the old code and passes against the new is
worth ten that only pass. When fixing a bug, check the test fails first
(`git stash` the fix, run it, unstash).

## Checking interface work in a browser

The node suite cannot reach pointer interaction, layout or canvas
output. Those are checked with the Chromium that is already installed:

```sh
cd web && python3 -m http.server 8123 --bind 127.0.0.1 &
npm install --no-save playwright-core     # in a scratch dir, not the repo
```

Launch it with `executablePath: '/opt/pw-browsers/chromium-1194/chrome-linux/chrome'`,
assert against `window.nanovna.state`, and always collect `pageerror`
and `console` errors — a silent exception during startup leaves an empty
topbar and every other assertion then fails confusingly.

**Two things that have bitten before:**

- `page.mouse` does not reliably honour pointer capture in this sandbox.
  Drag interactions here therefore attach their `pointermove`/`pointerup`
  listeners to `window` rather than relying on capture — which is also
  the only thing that survives a drag that reorders the DOM. If a drag
  needs testing another way, dispatch real `PointerEvent`s in the page.
- Clear `localStorage` and reload at the start of a check, or a previous
  run's saved layout will skew it.

## Things that are deliberately the way they are

- **Stop is not in a menu.** The sweep run buttons stay out in the
  topbar; only the parameters are behind the dropdown.
- **The frequency range bar is logarithmic.** An H4 tunes 10 kHz to
  1.5 GHz, and on a linear track everything below 100 MHz is unusable.
- **Visibility is a class, never the `hidden` attribute,** on anything
  with a `display` rule of its own: an author `display` declaration
  outranks the user agent's `[hidden] { display: none }`, which silently
  makes `hidden` do nothing.
- **The sweep range is re-read between passes,** so retuning a running
  continuous sweep works without stopping it.
